## Deploying to Azure

Everything the app runs on is described by the AppHost (`src/Sepiabox.AppHost`) and provisioned by azd in `rg-sepiabox`, France Central (S-032). Deploy only with the script, from the repository root:

```bash
azd env select sepiabox
./scripts/deploy.sh
```

It refuses to start unless the selected azd environment is `sepiabox` in `francecentral`, while `SEPIABOX_REGISTRY` or an `AZURE_CUSTOM_DOMAIN`, `AZURE_CUSTOM_DOMAIN_BINDING` or `AZURE_UPLOADER_PRINCIPAL_IDS` value is set, or while `customDomainBinding` is `SniEnabled` for a host name the web does not have yet (see "Custom domain"). It gives the AppHost parameters that are missing their "none" values (D-072), then:

1. `azd provision`: PostgreSQL `sepiabox-pg` (B1ms, 32 GB, auto-grow off, PostgreSQL 17, `vector` and `postgis` allowed), the storage account with its private containers (`originals`, `derivatives`, `manifests`, `incoming`, `exports`, `dataprotection`), Key Vault, the container registry (Basic), Application Insights on `sepiabox-logs`, the Container Apps environment, the managed identities (the web, the migrate and GeoNames jobs, the import jobs, and the faces job), the Service Bus namespace `sepiabox-bus` (Basic) with its `manifests` queue, and the Event Grid system topic that sends new manifests to it (S-033). The first run asks nothing: azd generates the PostgreSQL login and password and keeps them in `.azure/`.
2. Then `scripts/web-models.sh`, before anything touches the queue or the schema, so a failed build leaves everything as it was: the web's base image `sepiabox-web-models` with the CLIP text model (S-056, D-071). It is built and pushed only when the registry lacks the tag for this `models.json` and this ASP.NET Core image (it downloads the model with `models download --only`, which checks its SHA-256, into `SEPIABOX_MODELS` or the ingest's default folder: `%LOCALAPPDATA%\Sepiabox\models` on Windows, `~/.sepiabox/models` elsewhere); otherwise it is reused as it is. The script exports its name as `SEPIABOX_WEB_BASE_IMAGE`, so the web's image is built on it.
3. `azd deploy migrate`: builds the worker image and updates the `sepiabox-migrate` Container Apps job (manual trigger, 10 minutes, no retries).
4. Starts one execution of `sepiabox-migrate` (`sepiabox-worker migrate` against the cloud database) and waits for it, up to 15 minutes.
5. Only if it succeeded, `azd deploy import`, `azd deploy import-all` and `azd deploy faces`: the import jobs (S-033) and the hourly faces job (S-022, see "Turning face recognition off"), which expect the new schema and never migrate (D-063).
6. Then `azd deploy geonames`: the manual GeoNames job (S-059), which writes the new schema too and is only ever started by hand. If this step fails the queue receives again (the import jobs already run the new image), but the web is not deployed; run the script again.
7. Then `azd deploy web`: builds the web image and creates the `sepiabox-web` revision (0–1 replicas, HTTPS ingress, `AllowedHosts` = its default host).

If the migration fails, is stopped or times out, the script stops before step 5 and the running web is left as it was; the job's logs are in the `sepiabox-logs` workspace (table `ContainerAppConsoleLogs_CL`, container `migrate`). Fix the cause and run the script again: migrations already applied are skipped. `azd up` and a bare `azd deploy` are refused by the `predeploy` hook in `azure.yaml`, since they would start the web before the migrations.

**Keep the PostgreSQL login and password.** azd generates them once, on the first provision: the login in `.azure/sepiabox/config.json` (under `infra.parameters`, as `pg_username`), the password in azd's own local vault on that computer, with only a `vault://…` reference in `config.json`. Losing that folder does not regenerate them harmlessly: a new azd environment would generate a new login, which cannot be applied to the existing server, so provisioning fails; a new password alone would be applied, and the migrate job would fail to connect until its Key Vault reference refreshes (up to 30 minutes). So after the first provision, copy both values into a password manager, from the database vault as below (a backup of `config.json` alone keeps only the reference). They can also be read back from the secret `connectionstrings--catalog` (`Username=` and `Password=`) in the **database vault** (`databasevault-…`, which only the migrate job reads, D-062), which needs a Key Vault data role such as *Key Vault Secrets User* on that vault for your account: Owner on the resource group alone cannot read secrets. The third generated value, `pg_app_password` (the web's application role), needs no backup: if it is lost, the next deploy generates a new one and the migrate job sets it on the role before the web's new revision starts. If the first provision rejects the generated password (Azure's password rules), set a new one with `azd env config set infra.parameters.pg_password <letters and digits, with upper and lower case and a digit>` and provision again. To restore them on a new computer: `azd env new sepiabox --location francecentral --subscription <subscription id>`, then `azd env config set infra.parameters.pg_username <login>` and `azd env config set infra.parameters.pg_password <password>` (check the key names against your backup), and only then run the script. S-034's workflow supplies the same two values from GitHub secrets.

**Windows (Git Bash).** Git Bash rewrites arguments that start with `/` into Windows paths, which breaks `az` commands taking a resource id such as `--scope /subscriptions/…` (`MissingSubscription`). Run `export MSYS_NO_PATHCONV=1` first (or add it to `~/.bashrc`).

**The deploy hook is a guard, not a lock.** It only stops an accidental `azd up` or `azd deploy`; anyone who sets `SEPIABOX_DEPLOY_SCRIPT=1` by hand bypasses it. On Windows the hook runs in PowerShell 7 (`pwsh`), which must be installed; the script itself needs Bash.

**If azd cannot deploy one resource at a time.** The script relies on `azd deploy migrate`, `azd deploy import`, `azd deploy import-all`, `azd deploy faces`, `azd deploy geonames` and `azd deploy web` each deploying a single AppHost resource, and on azd deploying Container Apps jobs; neither could be tried before the first real deploy. If either is refused or a job is not created, deploy by hand in the same order:

1. The three AppHost parameters, each only if `azd env config get infra.parameters.<name>` finds nothing (D-072): `azd env config set infra.parameters.customDomain ""`, `azd env config set infra.parameters.customDomainBinding Disabled` and `azd env config set infra.parameters.uploaderPrincipalIds ""`. Then `export SEPIABOX_DEPLOY_SCRIPT=1 && azd provision --no-prompt`, then `SEPIABOX_WEB_BASE_IMAGE=$(scripts/web-models.sh)` (the web's base image with the CLIP text model), then pause the queue as the script does: `az servicebus queue update --resource-group rg-sepiabox --namespace-name sepiabox-bus --name manifests --status ReceiveDisabled`.
2. Generate the modules: `dotnet run --project src/Sepiabox.AppHost -- --publisher manifest --output-path .azure/publish`.
3. For each of `migrate` (project `src/Sepiabox.Worker`), then `import`, `import-all`, `faces` and `geonames` (the same project), then `web` (project `src/Sepiabox.Web`), in that order:
   For the web, add `-p:ContainerBaseImage=$SEPIABOX_WEB_BASE_IMAGE` to its `dotnet publish`, so the image carries the CLIP text model.
   1. Build and push its image: `az acr login --name <registry name>` (from `azd env get-values`, `AZURE_CONTAINER_REGISTRY_ENDPOINT` without `.azurecr.io`), then `dotnet publish <project> -c Release -t:PublishContainer -p:ContainerRegistry=<registry endpoint> -p:ContainerRepository=sepiabox/<resource> -p:ContainerImageTag=$(git rev-parse --short HEAD)`.
   2. Create or update it: `az deployment group create --resource-group rg-sepiabox --template-file .azure/publish/<resource>-containerapp.module.bicep --parameters <resource with - as _>_containerimage=<registry endpoint>/sepiabox/<resource>:<tag> ...`, giving every other parameter of the module its value from `azd env get-values`: the `AZURE_CONTAINER_APPS_ENVIRONMENT_*` and `AZURE_CONTAINER_REGISTRY_*` values give the `aca_outputs_*` parameters, and the vault, storage, access and identity outputs give the rest.
   3. After `migrate` only: run the job and wait for it as the script does (`az containerapp job start --name sepiabox-migrate --resource-group rg-sepiabox`, then `az containerapp job execution show ... --query properties.status` until `Succeeded`); stop here if it fails.
   4. After `geonames`: make the queue receive again (`... --status Active`).

The first deploy (2026-10-20) showed that single-resource deploys and the jobs work with azd, so these manual steps are only a fallback.

Until the owner creates the secrets below, the web starts with no sign-in buttons and lets no one in, but `/health` answers. On the first deploy the web may restart a few times while its new role assignments reach Key Vault (a few minutes); it then starts normally. The web's address is `https://sepiabox-web.<environment default domain>`: `az containerapp show --name sepiabox-web --resource-group rg-sepiabox --query properties.configuration.ingress.fqdn -o tsv`.

## Deploying from GitHub Actions

`.github/workflows/deploy.yml` (S-034, D-064) deploys `main` after CI passes on a push to it, and on demand (Actions → Deploy → Run workflow). It waits for approval in the `production` environment, signs in with OIDC (no secret), recreates the azd environment `sepiabox` from the saved parameters, runs `scripts/deploy.sh` (so a failed migration stops it before the import jobs and the web), and then keeps the last 5 images of every repository in the container registry. It never runs for pull requests. A run whose commit is no longer the newest on `main` ends in its first job, without asking for approval and without deploying, because the newer commit's own run deploys it. If that newer commit's CI fails, nothing is deployed until `main` is green again: fix `main`, or run Deploy by hand once it is green.

**The first deploy is from your computer** (`./scripts/deploy.sh`, see "Deploying to Azure"): azd generates the PostgreSQL parameters there, once. azd keeps generated secure parameters (`pg_password`, `pg_app_password`) in its own local vault and writes only a `vault://…` reference to `.azure/sepiabox/config.json`, so **never copy them from `config.json`**: a runner cannot resolve the reference (azd panics with a nil pointer, and the workflow now refuses such a secret). Copy the login and password from the database vault's secret `connectionstrings--catalog` instead, straight to GitHub without showing them (you need the GitHub CLI, `gh auth login`, and *Key Vault Secrets User* on that vault for your account; Owner on the resource group grants no data access):

```bash
dbvault=$(az keyvault list --resource-group rg-sepiabox --query "[?starts_with(name, 'databasevault-')].name | [0]" -o tsv)
az role assignment create --role "Key Vault Secrets User" --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --scope "$(az keyvault show --name "$dbvault" --query id -o tsv)"
# Wait a couple of minutes for the role to apply, then:
conn=$(az keyvault secret show --vault-name "$dbvault" --name connectionstrings--catalog --query value -o tsv)
printf '%s' "$conn" | sed -n 's/.*Username=\([^;]*\).*/\1/p' | tr -d '\n' | gh secret set PG_USERNAME --env production --repo sepiabox/sepiabox-platform
printf '%s' "$conn" | sed -n 's/.*Password=\([^;]*\).*/\1/p' | tr -d '\n' | gh secret set PG_PASSWORD --env production --repo sepiabox/sepiabox-platform
unset conn
gh variable set UPLOADER_PRINCIPAL_IDS --env production --repo sepiabox/sepiabox-platform \
  --body "$(jq -r '.infra.parameters.uploaderPrincipalIds // ""' .azure/sepiabox/config.json)"
```

`gh secret set` reads the value from its input, so it never appears on the screen or in the shell history. The database vault is also where the login and password can always be read back; the `.azure` folder alone is not a backup of them (it holds references), so keep a copy of `connectionstrings--catalog` in a password manager if you want one outside Azure.

`PG_APP_PASSWORD` (the web's application role) is not kept in Key Vault and `config.json` holds only a reference to it, so give the workflow a new one of 64 letters and digits, which the next deploy's migrate job gives the role before the web restarts: `LC_ALL=C tr -dc 'A-Za-z0-9' </dev/urandom | head -c 64 | gh secret set PG_APP_PASSWORD --env production --repo sepiabox/sepiabox-platform`. The workflow stops before azd if any of the three is missing, so azd never generates new ones on a runner (D-061).

After a workflow deploy, check the run's "Purge old images" step: one `acr purge` per repository, each keeping 5 images.

## Custom domain

The web answers at `https://app.sepiabox.com` once two azd parameters are set (S-035, D-065): `customDomain` (empty when unset: no custom domain at all) and `customDomainBinding` (`Disabled` when unset). Set them with `azd env config set infra.parameters.<name>`: azd reads them from the azd environment's `infra.parameters`, and `scripts/deploy.sh` sets them to these "none" values when they are missing (D-072). An `AZURE_CUSTOM_DOMAIN`, `AZURE_CUSTOM_DOMAIN_BINDING` or `AZURE_UPLOADER_PRINCIPAL_IDS` value, from `azd env set` or the shell, would take precedence over them in provisioning but not in the web's deploy, so the script refuses to run while one is set: remove it with `delete its line from `.azure/sepiabox/.env` (azd 1.36.0 has no `azd env unset`), or `unset <name>` in the shell. Deploys before that fix ignored them: if the steps below were already done, deploy again after it and run the checks of steps 3 and 4. Azure issues the free managed certificate only for a host name that is already on the app and whose CNAME points at it, so it takes two deploys, in this order:

1. **Find the two values.** The web's host: `az containerapp show --name sepiabox-web --resource-group rg-sepiabox --query properties.configuration.ingress.fqdn -o tsv`. The verification id: `az containerapp env show --resource-group rg-sepiabox --name "$(az containerapp env list --resource-group rg-sepiabox --query "[0].name" -o tsv)" --query properties.customDomainConfiguration.customDomainVerificationId -o tsv` (also the environment's output `AZURE_CONTAINER_APPS_CUSTOM_DOMAIN_VERIFICATION_ID`, in `azd env get-values` if azd keeps it).
2. **DNS at GoDaddy** (domain `sepiabox.com`): a CNAME record, name `app`, value the web's host from step 1; a TXT record, name `asuid.app`, value the verification id. Wait until `dig +short CNAME app.sepiabox.com` and `dig +short TXT asuid.app.sepiabox.com` return them.
3. **Add the host name.** Set `customDomain` to `app.sepiabox.com`, keeping `customDomainBinding` at `Disabled`. Always set the GitHub variables `CUSTOM_DOMAIN` (`app.sepiabox.com`) and `CUSTOM_DOMAIN_BINDING` (`Disabled`), even when you deploy from your computer: the Deploy workflow rebuilds the azd environment from them on every run, so a value set only locally is removed by the next workflow deploy. Locally also `azd env config set infra.parameters.customDomain app.sepiabox.com`. The workflow accepts only a plain host name and `Disabled` or `SniEnabled` (in any case), and stops otherwise. Deploy (`./scripts/deploy.sh` or the Deploy workflow). Check: `az containerapp hostname list --name sepiabox-web --resource-group rg-sepiabox -o table` lists `app.sepiabox.com` with binding `Disabled`. A deploy that fails here with a domain verification error means the TXT record is missing or not yet visible.
   **Before step 4:** sepiabox-infra's "Allowed resource types" policy must allow `Microsoft.App/managedEnvironments/managedCertificates` (sepiabox/sepiabox-infra#6) and sepiabox-infra's Deploy workflow must have run since; otherwise the policy refuses the certificate and the provision fails.
4. **Create and bind the certificate.** Set the GitHub variable `CUSTOM_DOMAIN_BINDING` to `SniEnabled` (and locally `azd env config set infra.parameters.customDomainBinding SniEnabled`) and deploy again: provisioning creates the managed certificate `sepiabox-custom-domain` (it can take several minutes), then the web binds it. Check: `az containerapp env certificate list --resource-group rg-sepiabox --name <environment> --managed-certificates-only -o table` shows it `Succeeded`, and the host name shows `SniEnabled`. On the next two deploys, check that the certificate is left alone: `az containerapp env certificate list --resource-group rg-sepiabox --name <environment> --managed-certificates-only --query "[].{state:properties.provisioningState,thumbprint:properties.thumbprint}" -o table` still shows `Succeeded` and the same thumbprint; report it if either changes. If the certificate fails, check that the CNAME points at the web's host from step 1 and that no CAA record on `sepiabox.com` forbids DigiCert, then deploy again.
5. **OAuth.** Add `https://app.sepiabox.com/signin-google` and `/signin-microsoft` to the Google and Microsoft OAuth clients (see "OAuth redirect URLs"), then run the S-035 owner check.

**If the binding is `SniEnabled` before the host name was added** (step 4 done before step 3 succeeded, or a new environment), provisioning would ask for the certificate before the web has the host name, and Azure refuses it. `scripts/deploy.sh` checks `az containerapp hostname list` first and stops with that message: set `CUSTOM_DOMAIN_BINDING` (and locally `infra.parameters.customDomainBinding`) back to `Disabled`, deploy, check step 3, then do step 4 again.

To remove the domain, set `CUSTOM_DOMAIN` (and `customDomain` locally) back to empty and `CUSTOM_DOMAIN_BINDING` to `Disabled`, and deploy. Deleting the certificate afterwards is optional (`az containerapp env certificate delete`); an unused managed certificate costs nothing. Browsers that visited the app keep using HTTPS for it for a year (HSTS, D-065), which is harmless since the app never serves plain HTTP.

## Secrets in Azure

There are two vaults in `rg-sepiabox` (D-062). The **owner's vault** (`vault-…`) holds what only the owner can provide; the web reads every secret in it as configuration, `--` standing for `:`, and reads them again every 5 minutes. The **database vault** (`databasevault-…`) holds the administrator's connection strings, written by the deploy and read only by the migrate job; never put anything there.

The deploy never creates the owner's secrets. Once, give yourself the right to write them (Owner on the resource group grants no data access):

```bash
vault=$(az keyvault list --resource-group rg-sepiabox --query "[?starts_with(name, 'vault-')].name | [0]" -o tsv)
az role assignment create --role "Key Vault Secrets Officer" --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --scope "$(az keyvault show --name "$vault" --query id -o tsv)"
```

Then set the secrets (a provider without both of its keys is left out, as locally):

```bash
az keyvault secret set --vault-name "$vault" --name Auth--Google--ClientId --value "<client id>"
az keyvault secret set --vault-name "$vault" --name Auth--Google--ClientSecret --value "<client secret>"
az keyvault secret set --vault-name "$vault" --name Auth--Microsoft--ClientId --value "<client id>"
az keyvault secret set --vault-name "$vault" --name Auth--Microsoft--ClientSecret --value "<client secret>"
az keyvault secret set --vault-name "$vault" --name Access--Emails --value "<e-mail>,<e-mail>"
az keyvault secret set --vault-name "$vault" --name Anthropic--ApiKey --value "<api key>"
```

When a secret applies: `Access--Emails` (and `Anthropic--ApiKey`, which the web reads when it uses it) within 5 minutes, when the web reads Key Vault again; the `Auth--*` sign-in secrets only when the web starts, so after creating or changing them restart the revision (`az containerapp revision restart --name sepiabox-web --resource-group rg-sepiabox --revision <latest revision>`), deploy a new revision, or wait for the web to scale from zero.

On the first deploy, and whenever the web's identity is new, its role on the vault takes a few minutes to propagate: until then the web cannot read Key Vault at start and fails, and Container Apps restarts it a few times before it starts normally. Do the owner checks only after that. Keep the values out of your shell history (for example, read them with `read -s`).

## Automatic import

Every manifest `upload` writes is imported without anything else to run (S-033, D-063): Event Grid sends the storage account's BlobCreated events for the `manifests` container to the `manifests` queue of `sepiabox-bus` (Service Bus Basic), and the `sepiabox-import` job, woken by KEDA within about 30 seconds of a message, imports until the queue is empty (one execution at a time, up to 30 minutes, then it scales back to zero). When an import fails because of the database or storage, the execution ends and the message comes back when its 5-minute lock expires, so its 5 deliveries are spread over about 25 minutes, which rides out a database restart; the fifth failure moves it to the dead-letter queue with the reason. A manifest that is itself invalid is logged and not retried. During a deploy the queue keeps its messages but nothing receives them, from after provisioning until the import jobs run the new image (`scripts/deploy.sh` makes it receive again on the way out, also when the migration fails; only when the migration succeeded and the import jobs could not be updated does it leave the queue paused and print the command to resume it once they run the new image).

**Backfill and reconcile.** `sepiabox-import-all` imports every new or changed manifest in the container (`import --once`; what is already imported is skipped). Run it once after the first deploy, for manifests uploaded before this story, and whenever the dead-letter count is not zero or the queue was disabled (the €45 shutdown disables it; Event Grid then retries for 24 hours and gives up). Don't run it while an upload is being imported: both jobs could insert the same new asset at once; the event-driven job then lets the message come back, but `import-all` reports that manifest as a problem until its next run.

```bash
az containerapp job start --name sepiabox-import-all --resource-group rg-sepiabox
az containerapp job execution list --name sepiabox-import-all --resource-group rg-sepiabox --query "[0].properties.status" -o tsv
```

**Dead letters.** Check the count:

```bash
az servicebus queue show --resource-group rg-sepiabox --namespace-name sepiabox-bus --name manifests --query countDetails.deadLetterMessageCount
```

When it is not `0`: find why in the job's logs (the `sepiabox-logs` workspace, table `ContainerAppConsoleLogs_CL`, container `import`; a database that was stopped or a failed deploy are the usual causes), fix the cause, then run `sepiabox-import-all`, which imports whatever the dead-lettered messages named. Then empty the dead-letter queue: Azure portal → `sepiabox-bus` → Queues → `manifests` → Service Bus Explorer → Dead-letter → Purge (your account needs *Azure Service Bus Data Owner* on the namespace for it). A manifest reported as invalid by both jobs needs a new `process` and `upload` of its file.

**Check after the first deploy that the job starts.** The job's scale rule reads the queue's length as the import identity (`import-identity`), which has *Azure Service Bus Data Owner* on the `manifests` queue only: reading the length needs the Manage claim. Upload one small folder; within about 30 seconds `az containerapp job execution list --name sepiabox-import --resource-group rg-sepiabox --query "[0].{status:properties.status,start:properties.startTime}" -o table` shows a new execution. If none appears while messages wait (`az servicebus queue show --resource-group rg-sepiabox --namespace-name sepiabox-bus --name manifests --query countDetails.activeMessageCount`), look for scale rule errors (KEDA, `azure-servicebus`, 401 or Unauthorized) in the `sepiabox-logs` workspace, table `ContainerAppSystemLogs_CL`, for `sepiabox-import`, and report them; meanwhile `sepiabox-import-all` imports the waiting manifests.

**Check after the first deploy how failures are retried.** The job leaves a failed message locked so that it comes back only when its 5-minute lock expires (D-063); whether ending the execution releases the lock earlier is not verified. Once, at a quiet moment: stop PostgreSQL (`az postgres flexible-server stop --name sepiabox-pg --resource-group rg-sepiabox`), upload one small folder, wait about 15 minutes, start PostgreSQL again (`az postgres flexible-server start ...`), then list the import executions (`az containerapp job execution list --name sepiabox-import --resource-group rg-sepiabox --query "[].{status:properties.status,start:properties.startTime}" -o table`). Failed executions about 5 minutes apart confirm the assumption, and the message is imported once PostgreSQL is back. Executions about 30 seconds apart mean the lock is released when the receiver closes: report it, so the job can wait for its lock to expire before exiting, or defer the message instead. Check the dead-letter count afterwards.

KEDA may also start short executions that find nothing to receive, or fail, while a message is locked or the queue is paused during a deploy; they cost seconds and need no action.

**First provision.** If the first `azd provision` fails on the event subscription `manifests-to-queue` with an authorization error, the system topic's new role on the queue has not reached Event Grid yet: wait a few minutes and run the script again.

**Names.** A storage account can have only one Event Grid system topic (`sepiabox-storage-events`); if one already exists on the account, delete it or reuse its name in `Bicep/events.bicep`. `sepiabox-bus` is a global name: if Azure reports it as taken, change it in `AzureInfrastructure.ServiceBusName` here and in the shutdown runbook's `ServiceBusNamespace` in sepiabox-infra (`automation/Stop-Sepiabox.ps1`, `scripts/resume.sh`, `scripts/emergency-stop.sh`) in the same change, with the test constant `ShutdownRunbook.ServiceBusNamespace`.

## Place names (GeoNames)

Photos get a place ("Matosinhos, Porto, Portugal") from the GeoNames cities loaded in the catalog: the nearest city within 50 km of the photo's location, when it is imported (S-012, D-066). Until the cities are loaded, assets are imported without a place.

**In Azure** the manual job `sepiabox-geonames` loads them (S-059, D-067). It runs `sepiabox-worker geonames update`: downloads the three files over HTTPS from `download.geonames.org` (nothing else is accepted, and redirects are not followed) into the replica's temporary storage, logs each file's SHA-256, size and date, refuses the load when `cities500` has fewer than 150,000 cities or more than 10% fewer than the table holds now, replaces the cities in one transaction (any failure keeps the previous ones), then names the assets that have a location and no place. It connects as the PostgreSQL administrator (it writes `geonames`, which the application role may only read) with the migrate job's identity, and needs outbound HTTPS, which the Container Apps environment has (no VNet). A run takes a few minutes at 1 vCPU and 2 GiB, billed only while it runs (D-008).

- **Once after the first deploy** (and after any deploy that recreated the database), start it and wait for `Succeeded`:

  ```bash
  az containerapp job start --name sepiabox-geonames --resource-group rg-sepiabox
  az containerapp job execution list --name sepiabox-geonames --resource-group rg-sepiabox --query "[0].{status:properties.status,start:properties.startTime}" -o table
  ```

- **Again to refresh**, only when places are missing (a city founded or renamed, a large upload of old photos from places GeoNames lacked); GeoNames changes slowly, so there is no schedule. A refresh does not rename places already set (D-066). To name every asset again after it, start one more execution with the container's arguments overridden to `places refresh --all` (`az containerapp job start` takes the job's image and new arguments for one execution; this was not tried before the first real deploy, so check `az containerapp job start --help` for the exact form).
- **Check the logged hashes** of each run in the `sepiabox-logs` workspace (table `ContainerAppConsoleLogs_CL`, container `geonames`, lines starting "Downloaded"): the size and date should be plausible (cities500.zip about 10 MB, dated within the last days), and you can compare the hash with a copy downloaded on your own computer the same day (`sha256sum cities500.zip`). A refused load ("fewer than the 150000 expected at least", "fewer than the N loaded now") or a download error ends the execution as `Failed` and keeps the cities already loaded: check https://download.geonames.org/export/dump/ and start it again later. **A 3xx status in the log** ("answered 301", "answered 302") means GeoNames moved the files: check the dump page and update `GeoNamesDownloader.DefaultBaseUri` (`src/Sepiabox.Worker/Places/GeoNamesDownloader.cs`) to the new HTTPS location on `download.geonames.org` in a pull request; the job never follows a redirect by itself.
- **Renamed cities.** An update loads GeoNames' new names but does not rename places already set on assets (D-066). When you want them applied, run the job once more with its arguments overridden to `places refresh --all`, as described above.

Until the job has run, the search's country filter (`places.countries`, S-013) matches nothing: it goes through the GeoNames country names (D-069). City filters still match the names already on the assets.

**Locally**, load them yourself (the catalog of `dotnet run --project src/Sepiabox.AppHost`, or any catalog in `ConnectionStrings__catalog`, with an administrator connection):

1. Download `cities500.zip`, `admin1CodesASCII.txt` and `countryInfo.txt` from https://download.geonames.org/export/dump/ into a folder outside the repository. GeoNames is CC BY 4.0: never commit these files.
2. Run `dotnet run --project src/Sepiabox.Worker -- geonames load <folder>/cities500.zip --admin1 <folder>/admin1CodesASCII.txt --countries <folder>/countryInfo.txt`. It replaces the cities in one transaction (about 200,000 rows, a minute or two), so running it again with newer files is safe, and a failed load keeps the previous cities.
3. Run `dotnet run --project src/Sepiabox.Worker -- places refresh` to name assets imported before the load. It only names assets that have a location and no place, so it is safe to run again.
4. Loading a newer dump does not rename places already set. To name every asset again from the new cities, run `places refresh --all`.

The application role `sepiabox_web` can read the cities but not change them: load them with the administrator connection (D-066).

## Occasions

Photos and videos are grouped into occasions (a wedding, a trip) by `sepiabox-worker events rebuild` (S-023, D-092): a new occasion starts after a gap of more than 6 hours between two dated assets, or when an asset is more than 50 km from the previous geotagged one. Nothing groups them by itself yet: **run it after importing**, or the new photos are in no occasion and the **Occasions** page does not show them. It is safe to run again: with the same assets it changes nothing, and occasions keep their ids.

- **Locally**: `dotnet run --project src/Sepiabox.Worker -- events rebuild` against the catalog in `ConnectionStrings__catalog`.
- **In Azure** there is no job for it yet. The `sepiabox-geonames` job (`src/Sepiabox.AppHost/AppHost.cs`: the worker image, started with the arguments `geonames update`, and `migrate`'s identity, so it connects to the database as the administrator) can run it: start one execution with the arguments overridden to `events rebuild`, probably `az containerapp job start --name sepiabox-geonames --resource-group rg-sepiabox --args events rebuild` (not verified offline: check `az containerapp job start --help`, and if it asks for `--image` and `--container-name`, copy them from `az containerapp job show --name sepiabox-geonames --resource-group rg-sepiabox`). After the first run, look for the log line "Rebuilt the occasions: …" in the execution's logs. Running it locally, as above, is the form that can be checked first. A later story can add a job of its own.
- **Types.** A rebuild keeps an occasion's type (S-024) only while its assets are exactly the same; one that gained or lost an asset has no type again, and classifying (S-024) gives a type to every occasion without one.
- **Types (S-024, D-094).** After a rebuild, `sepiabox-worker events classify` gives a type (wedding, birthday, beach, christmas, graduation, snow, party, trip) to every occasion that has none, including those a rebuild cleared; occasions that already have one are left as they are, and one nothing fits stays without a type and is looked at again by the next run. It needs the CLIP text model on the computer that runs it: `sepiabox-ingest models download --only clip-vit-b32-text,clip-bpe-vocab` once (or `Search:ModelFolder`), then `dotnet run --project src/Sepiabox.Worker -- events classify`. It cannot run in Azure yet: the worker image has no text model (only the web's has, S-056), so classify from your computer against the catalog, as for the rebuild. Run it after every rebuild, or new and changed occasions stay without a type and the occasion filters and counts do not see them. A `trip` needs a place marked as home (**Places**), and **trip counts are unreliable for now**: a trip of several days is usually one occasion per day (S-023 splits after 6 hours), so "a day or more" almost never holds; [sepiabox/sepiabox-platform#84](https://github.com/sepiabox/sepiabox-platform/issues/84) will group consecutive occasions away from home. A type is not looked at again once given, even if only some of the occasion's photos had embeddings then.
- **Owner acceptance.** After the first `events classify` on the real library, open about 20 occasions of different types on **Occasions** (`?type=`), and compare the numbers of each type with what you remember (how many weddings, how many beach days): a type that is far too common means the photos' CLIP embeddings or the prompts need another look (D-094).
- Assets without a capture date are in no occasion. Re-running `places refresh` renames places on assets, not on occasions: run `events rebuild` after it for their labels to follow.

## Blurry photos and bursts

**Compatibility.** Older builds of `sepiabox-ingest` and `sepiabox-worker` reject a manifest that has `quality`, so deploy the worker first and update every computer that runs `sepiabox-ingest` before it uploads such a manifest. **The first run is big:** `process` adds `quality` to every unchanged photo manifest, so `upload` rewrites all of them (about 86,000 blobs, with new ETags) and the import re-imports the whole library once. It is harmless but slow; expect it, and do not stop it halfway for a quicker one.

Run `sepiabox-ingest process` again on each work folder (S-027, D-098): every photo gets its sharpness and a 64-bit hash in its manifest, from the preview already in the folder, so the drive does not need to be connected; then upload as usual and the import stores them (`sepiabox-ingest upload`, then the automatic import, or `sepiabox-worker import`). Photos processed before this have none until then and are not offered as blurry or in a burst. Open **Organize** in the web app: bursts (photos taken within 2 seconds of each other that look alike, the sharpest left unchecked), photos below the blurry threshold (`Search:BlurryBelow`, 100 by default; raise it to see more) and what was set aside. "Set aside" only hides a photo from search, counts and the timeline; nothing is deleted and no original is touched. Bring it back from the **Set aside** list, or find it in a search with `"includeHidden": true` in the filters of `POST /api/search`. A re-import never brings a set-aside photo back. Questions in the search box do not ask for blurry photos yet. A burst shows at most 12 photos (a longer run is cut), and photos from two cameras shooting in turns do not form bursts. **Owner check:** after the first import, open **Organize**, **Blurry**, and look at about 20 photos near the threshold (their sharpness shows in the tooltip): if clearly blurry ones are missing, raise `Search:BlurryBelow`; if sharp ones are listed, lower it. 100 is a first guess.

## Uploading the drive to Azure

1. Once: be listed in `uploaderPrincipalIds` (see the prerequisites) and run `az login` on the computer with the work folder; `upload` signs in with `DefaultAzureCredential`, so the Azure CLI login is enough.
2. Run `sepiabox-ingest upload <work folder> --destination azure --account <storage account name>` (the name is in the azd outputs).
3. It resumes where it stopped: run the same command again after an interruption. Originals go to the Cold tier and each is read once (D-030); manifests go last, so the cloud imports only complete assets (S-033). Except from a work folder made by `process --index-only` (D-088, S-063): no originals are uploaded, and the drive or export folder does not need to be connected.
4. A file reported as changed since `process` is not uploaded: run `process` again for it.
5. Never run `upload` while `sepiabox-worker assets delete --yes` runs (S-057, after the MVP): a manifest uploaded during the deletion can lose its blobs.

## Ingesting a drive

- Run `sepiabox-ingest models download` once per computer before `process`, so embeddings (and faces, with `--faces`) are computed in the same pass.
- **Speed (D-078).** `process` handles several files at once: `--jobs <n>` (1 to 64, half the computer's processors by default) and `--video-jobs <n>` (videos read and transcoded at once, 1 by default). The drive is still read by one reader, front to back, each photo once; the manifests and derivatives are the same for any `--jobs`. If the computer is already at about 100% CPU, more jobs gain little: compare the files per second the summary gives (files ÷ time) for `--jobs 1`, `2` and `4` on a folder of a few hundred photos (a fresh `--out` each time) and keep the fastest. Each job holds a decoded photo in memory (about 100 MB at 24 MP, 400 MB at 50 MP) besides up to 256 MB of photos read ahead, so lower `--jobs` when memory is short or the drive has many RAW files. A run in progress can be stopped with Ctrl+C at any time: what was finished is kept, and running `process` again with the same `--out` (with a new build or other `--jobs`) carries on from there.
- **Index-only mode keeps no copy of the originals (D-088, S-063).** With `process --index-only`, the originals stay on the drive or in the export folder and are never uploaded; Sepiabox keeps only its previews (photos up to 2048 px, videos at 1080p) and the address of each original. If the drive or the source loses an original, Sepiabox cannot give it back: keep your own backup of anything processed this way. A work folder holds one mode; work folders made before index-only mode keep their originals. The first `process` run records the mode in the work folder's `state.db`, `upload` follows it, and `process` on the same `--out` asking for the other mode stops at once, before reading a file, with exit code 2 and "This work folder is index-only (or: keeps originals); use a new --out for the other mode." Your existing work folder counts as keeping originals; `--index-only` on it is refused, so use a new `--out`. `upload` from an index-only work folder sends only previews and manifests, needs neither the drive nor the export folder, and ends its summary with "originals left at their source N" (D-091). A 1080p version takes noticeably longer to transcode than a 720p one, so expect an index-only run over many videos to be slower.
- **Switching a source between modes (D-088, D-091).** From index-only to keeping originals: run `process` on the same source into a new work folder without `--index-only`, then `upload` from it. The stored manifest then says the original is stored, the original is in storage, and the previews of both runs are kept side by side (`preview-1280` and `preview-2048`; the web shows the larger one). The other way, removing originals already in storage, is not supported yet: it would delete blobs, so it needs its own story.
- **A wrong stored source url (S-063, D-091).** Merging keeps the greatest url ever uploaded for a source, so uploading a corrected one does not replace a greater old one. To repair it, delete that asset's manifest blob (`manifests/<id>.json`) in storage and upload again from the work folders, as for a wrong date (D-046); the import then replaces the catalog's url.
- Manifests written by `process --index-only` carry `originalStored: false` (S-063, D-088), and a source may carry `url`. Older `sepiabox-ingest` and `sepiabox-worker` builds reject both, so update every computer that runs `sepiabox-ingest` and deploy the worker (it also applies the catalog migration `OriginalStoredAndSourceUrl`) before the first index-only upload; otherwise `upload` from an old build fails to merge those manifests (that asset is reported and retried, the stored blob is left alone) and the old worker's import reports them as problems.
- Faces are opt-in (biometric data): only `process --faces` looks for them (S-018, D-047). Decide before the first full run of the drive; a later run with `--faces` adds them from the work folder without the drive, as long as the work folder is kept.
- Before the first full run, check one of your own Canon `.CR2` files. The tests only use a synthetic CR2 (D-045).
  1. Copy the file into a new, empty temporary folder.
  2. Run `process` on that folder with a separate, new `--out` folder.
  3. Open `derivatives/<id>/preview-1280.webp` in that `--out` folder. It should look like the camera's JPEG: right colours, upright, not a 160x120 thumbnail blown up.
  4. Delete both folders. Never `upload` from that `--out` folder: its manifest names the temporary copy as a source.
- `process` lists each file it leaves out ("Left out <path>: <reason>") next to its problems: a tracker-music module, or a file with no video stream or only cover art (D-045). Left-out files are never catalogued. If one is a real video, report it. Later runs only count the files left out earlier; `--list-left-out` lists them, and `--retry-left-out` reads them again (for example after installing a different FFmpeg). Never `touch` or re-save the originals to force a retry: their modification time is the only capture date some camcorder files have.
- **Keeping a log of a run.** In PowerShell: `sepiabox-ingest process <drive> --out <work folder> | Tee-Object -FilePath process-log.txt`. Only the standard output goes to the log, on purpose: the progress counter goes to the screen through the standard error, and the summary, the files left out, the videos made without sound and the problems are all listed at the end, on the standard output, so they are in the log. Do not add `2>&1`: Windows PowerShell 5.1 turns each standard error line into a red "NativeCommandError" record that looks like a failure but is not one. The warnings (missing embeddings or faces, a missing FFmpeg) also go to the standard error, so read them on the screen.
- **NVENC needs a recent NVIDIA driver (`--hw nvenc`, D-087).** FFmpeg's `h264_nvenc` only opens with a driver at least as new as the NVENC API FFmpeg was built for: a recent FFmpeg (NVENC API 13.1) needs driver 610.00 or newer. With `--hw nvenc`, `process` first encodes a generated half-second clip with the same settings (in a temporary file in the work folder, deleted afterwards; the drive is not touched). If that fails it stops before processing anything, with exit code 1, printing "The NVIDIA encoder (--hw nvenc) cannot encode on this computer, so nothing was processed. FFmpeg said: …" and the fix: update the NVIDIA driver to the version FFmpeg asks for (or newer) and run the same command again, or run it without `--hw nvenc` to encode on the processor (slower). It never falls back to the processor on its own. To see the driver version, run `nvidia-smi --query-gpu=name,driver_version --format=csv` in a terminal. Consumer NVIDIA drivers allow only a few encoding sessions at once (about 8), so `process` runs at most 4 NVENC encodes at a time whatever `--jobs` says; more jobs still help the photos.
- **Videos made without sound (D-084, D-087).** Some SD camcorder `.MOD` and `.MPG` files declare a sound stream FFmpeg cannot decode a single frame of; they play without sound. When a 720p version cannot be made with sound, `process` decodes the first frame of the file's sound: only when not one frame decodes is the 720p version made without sound, and the file listed at the end of the run ("Made without sound <path>: <FFmpeg's message>", counted in the summary as "made without sound"). Any other failure, such as an encoder that cannot open (whose FFmpeg message also ends in "at least one of its streams received no packets"), stays a problem ("Could not make the poster and 720p version: ffmpeg failed: …", with every line FFmpeg printed, the cause first), and the next run tries the file again. Builds with D-084 alone made a 720p version without sound after any failure, so an NVENC failure dropped sound that works. After updating `sepiabox-ingest` (and the NVIDIA driver, or without `--hw nvenc`), run the same `process` command again with the same `--out`: files that failed are redone, and so is every video done by an earlier build whose 720p version has no sound while the source's sound decodes (checked once: the 720p version in the work folder, then, only when it is silent, the start of the source on the drive; a source without sound, or whose sound does not decode, is just recorded as such). Files already done are skipped. Then `upload` as usual: the new 720p versions replace the ones without sound in storage.
- Keep the `process` work folder (`manifests/` and `derivatives/`) until every file has its embedding, and its faces if you use `--faces`: a later `process` run adds them from the previews in the work folder without the drive, but cannot once they are deleted. The summary has no "have no embedding" or "no preview or poster" warning when nothing is left to add.
- Manifests written by `process` from S-043 on may carry `capturedAtSource` (D-046). Older `sepiabox-ingest` and `sepiabox-worker` builds reject that field, so update every computer that runs `sepiabox-ingest` and deploy the worker before uploading such manifests; otherwise `upload` from an old build fails to merge them and the old worker's import reports them as problems.
- Manifests written by `process --faces` carry faces and `facesVersion` (S-018, D-047). Older `sepiabox-ingest` and `sepiabox-worker` builds reject `facesVersion`, so update every computer that runs `sepiabox-ingest` and deploy the worker before uploading manifests from a `--faces` run; otherwise `upload` from an old build fails to merge them (that asset is reported and retried, the stored blob is left alone) and the old worker's import reports them as problems.
- **Locations of videos processed by older builds (S-060, D-089).** The first `process` run with the same `--out` after updating records every file's metadata version once (fast: one small write per file, nothing read from the drive), and reads the header of each MP4, MOV, M4V or 3GP video whose manifest has no location, once, even in a work folder processed after S-053; most of those videos simply have no location and gain nothing. Nothing is hashed or made again, and photos and camcorder files are not read. The summary says "metadata refreshed M, locations added K"; then run `upload` to send the manifests that changed. Later runs read nothing again.
- Files processed before S-043 keep the date they had (none, for undated videos): `process` skips unchanged files. To date them from their folder or file name, run `process` again into a fresh work folder and upload from it.

## Importing exports (after the MVP)

Google Photos, Apple Photos / iCloud, Instagram and Facebook are imported from their official exports (D-053, Sprints 15–16, renumbered by D-090; with `--index-only`, D-088, their originals stay in the export folder), which only the account owner can request:

| Source | How to get it |
|---|---|
| Google Photos | takeout.google.com → only Google Photos → zip parts; extract them all into one folder |
| Apple Photos | On a Mac, Photos → File → Export → Export Unmodified Originals (tick "Export IPTC as XMP"); or privacy.apple.com → Request a copy of your data → iCloud Photos |
| Instagram, Facebook | Accounts Center → Your information and permissions → Download your information → format **JSON**, media quality high |

Keep the extracted export on the PC and run `sepiabox-ingest process <folder> --export <kind>`; the export is only read. Exports hold personal data: never commit them or attach them to issues. When a story asks for a small real export to confirm the format, share it privately with the person running it. S-046 to S-049 each need one (a few photos or posts and one album, see the prerequisites); without it the story is `blocked` with the reason "needs a small real export to confirm the format".

**`process --export <kind> [--time-zone <IANA id>]` (S-045, D-104).** `--export` names the kind of export the folder holds; the readers for each service arrive with S-046 to S-049, and `sepiabox-ingest process --export x` lists the kinds known so far. What the export says is added to what the files say, in this order for the date (D-046): the file's own metadata, then the export, then the file name, then the folder; the manifest's `capturedAtSource` is then `export`. An export's UTC times are shown as wall-clock time in `--time-zone` (for example `Europe/Lisbon`; default: this computer's zone) and stored without an offset (D-037); a time the export gives without a zone is used as it is. The export's location fills `location` only when the file has none (`0,0` counts as none), and its caption (cut at 2,000 characters) and albums are kept in the manifest for S-052 to show. The export folder is only read. **`--time-zone` takes an IANA id (`Europe/Lisbon`) on every system, and on Windows a Windows id (`GMT Standard Time`) too.** Captions and album names are stored in Unicode form C. An export date before 1990 is not used (a device's reset clock looks the same); the folder's date still is. **Never upload the same folder both as a plain run and as an export:** each file would carry two sources, `local` and the export kind. **Run `process --export` on a new `--out`, and on the whole export in one go**: a file already processed in that work folder is not read against the export again, so an export added to an older work folder does not change its unchanged files; copies of the same bytes inside one run do merge what each says (the longer caption, the union of the albums, the stronger date).

**Google Photos (S-046, D-106).** Request the export at takeout.google.com (only Google Photos, JSON is the default) and extract every `takeout-*.zip` part into one folder, so a photo and its JSON sidecar are in the same place. Then `sepiabox-ingest process <folder> --export google-takeout --time-zone <your zone> --out <work folder>` (add `--index-only` to leave the originals in the export folder, D-088). Each photo or video gets its taken time from `photoTakenTime`, its place from `geoData` (else `geoDataExif`), its caption from `description` and its albums from the folders it is in (the title in the album's `metadata.json`, else the folder's name; `Photos from YYYY` folders are not albums), and the source's `url` is its address in Google Photos when the sidecar has an `https://` one. A photo with no sidecar is read from its own metadata and counted in one warning. Faces and people names in the sidecars are not read. Items in the export's `Trash` folder (in any language) are not imported, and the run says how many (a sidecar's `trashed` flag, when there is one, decides instead of the folder's name); `Archive` is not an album, so archived photos are imported without one (D-106). The first run on a real export is the owner's check of the formats (see "Owner acceptance").

**Apple Photos and iCloud Photos (S-047, D-109).** Two exports are read, alone or together in one folder. On a Mac, Photos → File → Export → Export Unmodified Originals with "Export IPTC as XMP" ticked gives the originals and an `.xmp` per file with the description, the date and the place; or request your data at privacy.apple.com (iCloud Photos), extract every zip part into one folder, and the `Photo Details*.csv` files give each photo's `originalCreationDate` (UTC) and a `deleted` flag, and the CSVs in `Albums` give the albums. Then `sepiabox-ingest process <folder> --export apple-photos --time-zone <your zone> --out <work folder>` (add `--index-only` to leave the originals in the export folder, D-088). A photo marked deleted is not imported and is counted in the report; a photo with no row in `Photo Details` is read from its own metadata. Files are matched to CSV rows by file name, so a name that two files share gets nothing from the CSV. `.AAE` edit files are ignored. No source has a link: Apple has no address for a photo, so the detail page says where the original is (S-064). Apple documents none of these files; if the report warns about dates in an unknown format or an album list that names no file, send the owner the layout (file names and the header row, no personal data).

**Instagram (S-048, D-111).** Request the download at Accounts Center → Your information and permissions → Download your information: your Instagram account, **format JSON**, media quality high, date range all time; extract every part into one folder. Then `sepiabox-ingest process <folder> --export instagram --time-zone <your zone> --out <work folder>` (add `--index-only` to leave the originals in the download, D-088). The post lists (`your_instagram_activity/content/posts_1.json`, `archived_posts.json`, `stories.json`, `reels.json`) give each photo or video its caption and its date: the camera's date when the post has one, else the posting time (an approximation of when it was taken, as Instagram strips the files' own metadata). Albums are `Instagram`, plus `Instagram stories` and `Instagram reels`. Photos and videos that no list names (profile pictures, messages) are not imported and are counted in the report; **the count may include your own highlights, IGTV and archived stories if the download keeps them in lists this reader does not read, so check it against your account**. A story's or reel's date is when it was posted. No source has a link: the lists carry none. Instagram changes the layout between versions; if the run stops with "No Instagram post list was found", send the owner the folder names (no personal data).

**Facebook (S-049, D-112).** Request the download at Accounts Center → Your information and permissions → Download your information: your Facebook account, **format JSON**, media quality high, date range all time; extract every part into one folder. Then `sepiabox-ingest process <folder> --export facebook --time-zone <your zone> --out <work folder>` (add `--index-only` to leave the originals in the download, D-088). The album files (`your_facebook_activity/posts/album/<n>.json`) and the posts file (`posts/your_posts__check_ins__photos_and_videos_1.json`) give each photo or video its caption (its description, else the post's text), its date (when it was taken, else when it was posted) and its albums (the album's name, as Facebook names it, and `Facebook`). Photos and videos that no list names (Messenger, profile pictures) are not imported and are counted in the report; check that number against your account. No source has a link: the lists carry none. Facebook changes the layout between versions; if the run stops with "No Facebook album or post list was found", send the owner the folder names (no personal data).

**Compatibility (as D-046, D-047, D-098).** The manifest gets two new top-level properties, `caption` and `albums`, and a new `capturedAtSource` value, `export`. Older builds of `sepiabox-ingest` and `sepiabox-worker` reject a manifest that has any of them (the schema forbids unknown properties and values), so **deploy the worker first, and update every computer that runs `sepiabox-ingest` before it processes or uploads an export**; a manifest with none of the three, which is every manifest until the first export is processed, reads exactly as before. Nothing in the catalog changes: the web ignores `caption` and `albums` until S-052. A caption never gets shorter and an album never leaves a photo through a later export (every source is add-only, D-036).

## People

Faces found by `process --faces` (S-018) are grouped into people when their manifests are imported (S-019, D-077): a face joins the person whose average face (centroid) is most similar, from a cosine similarity of 0.40 (D-016), or starts a new, unnamed person. The **People** page lists them, most faces first. Naming, merging and correcting people is S-020.

- **After the deploy that brings S-019,** its migration makes the import read every manifest again, so faces uploaded before it reach the catalog (re-importing changes nothing else, D-032). Don't upload until this is done. Then:
  1. Start `sepiabox-import-all` and check its execution (commands under "Automatic import"): `az containerapp job execution list --name sepiabox-import-all --resource-group rg-sepiabox --query "[0].{status:properties.status,start:properties.startTime,end:properties.endTime}" -o table`.
  2. Expect it to take a while: every manifest is downloaded and imported once more. As a rough guess (not measured in Azure), count tens of manifests a second, so several minutes for 10,000 assets; a large library or a busy database can pass the execution's 30-minute limit, and a library of about 100,000 assets should expect two or three executions.
  3. If it ends `Failed` (a timeout included), start it again: it skips what is already imported and carries on. Repeat until one execution ends `Succeeded`; until then the library is only partly imported (the timeline is complete, but faces and people may be missing).
  4. Check that the dead-letter count is `0` (see "Automatic import").
- **The threshold** is `People:SameFaceThreshold` (0.40 unless set; above 0 and at most 1), an environment variable `People__SameFaceThreshold` of the import jobs. A higher value splits one person into several more often, a lower one merges different people. It applies to faces imported from then on; faces already grouped stay where they are.
- **A manifest without faces looked for** (`process` without `--faces`) never removes faces already imported; a new `--faces` run replaces an asset's faces and keeps each face's person when it is found again in about the same place (D-047).

### Turning face recognition off

Faces are biometric data (LGPD/GDPR). **Settings** in the header (`/settings`) has the library's face recognition switch (S-022, D-081). It is on unless someone turned it off; `process --faces` on each computer remains the opt-in for looking for faces.

- **Turning it off** asks on the page first, then deletes every face and every person, with their names, centroids and "This is me", in one transaction that waits for any import in progress. The photos stay. Each deletion is recorded (when, by whom, how many faces and people) and listed on the page.
- **While it is off**, imports store no face, whatever the manifests hold.
- **After deploying S-022, update `sepiabox-ingest` on every computer** before its next upload and before anyone turns recognition off: older builds reject manifests with `facesErasedAt` or `facesDetectedAt` (so their uploads of an erased asset fail), and an older `process --faces` writes no `facesDetectedAt`, so its faces count as found before any erase and are never imported after one.
- **Clocks.** `upload` refuses to send anything when the computer's clock is more than 5 minutes from the storage server's; set the clock to synchronize with internet time (on Windows: Settings → Time & language → Date & time → Sync now) and upload again. Faces are kept or erased by the time they were found, and faces said to be found more than 6 minutes after their manifest was uploaded (a clock that was ahead when `process` ran) are left out by `upload` (with a warning: run `process --faces` into a fresh work folder), dropped by the next merge into that manifest, never imported, and erased by the sweep.
- **The stored manifests.** The manifest blobs in Blob Storage hold the faces' embeddings too. The `sepiabox-faces` job (`sepiabox-worker faces sweep`, every hour at minute 17) stamps the erase time (`facesErasedAt`) into every manifest through the same merge as `upload` (D-036): faces found at or before it are removed, and no later upload of them brings them back. Its first pass after an erase reads and rewrites every manifest, 24 at a time; a run stops after 25 minutes and the next hour's run carries on from where it stopped, so on a large library (about 86,000 manifests) the pass takes a few hours. Later passes only read manifests written since. Until the first pass is complete the page says so, and recognition cannot be turned back on. Check it with `az containerapp job execution list --name sepiabox-faces --resource-group rg-sepiabox --query "[0].{status:properties.status,start:properties.startTime}" -o table`; each run's log line says whether its pass finished and whether it was recorded (`pass finished: True, recorded: True` ends the erase). A run that ends `Failed` names, in its logs, the manifests it could not read; fix or delete them, and the next run starts the pass again (a pass with a problem is never recorded). Locally, run `dotnet run --project src/Sepiabox.Worker -- faces sweep` against the local environment's connection strings.
- **A burst of imports.** Each manifest the first pass rewrites raises a BlobCreated event, so the import jobs re-import every manifest once (about 86,000 `sepiabox-import` messages on a large library). This is harmless (nothing changes but the import times) and shows in the import executions and the queue's message count for those hours.
- **Turning it back on** imports only faces found after the erase (`facesDetectedAt`, written by `process --faces` from this version on). Faces in work folders processed before it, and faces written before the field existed, never come back.
- **Work folders.** Each computer that ran `process --faces` keeps the faces in its work folder (`manifests/*.json`). Uploading it again does not bring them back to the cloud, but to delete them from that computer too, delete the work folder, or run `process` into a fresh work folder without `--faces` (and delete the old one). A work folder kept after turning recognition off cannot find faces again: its manifests already count as looked for, so after turning it back on, run `process --faces` into a fresh work folder.
- **Backups.** PostgreSQL's point-in-time restore and the storage account's soft delete keep deleted face data, including the manifest versions the sweep overwrites, for up to 7 days; after that it is gone. A restore within those 7 days brings the deleted faces back: turn recognition off again after one.
- **Deleting one person's face data** ("Delete face data" on a person's page, with a confirmation) deletes the person and their faces; the photos stay. Only the boxes of their faces are kept (no embedding), so a later import of the same photos does not find them again. The stored manifests still hold those faces' embeddings until face recognition is turned off.

## Search by description

The filter bar's "Describe (in English)" box (S-016) compares a description with the photos' CLIP embeddings. It appears only when the web finds the CLIP text model and tokenizer, both pinned in `models.json`: locally in the folder `sepiabox-ingest models download` fills (`SEPIABOX_MODELS`, or by default `%LOCALAPPDATA%\Sepiabox\models` on Windows and `~/.sepiabox/models` elsewhere; `Search:ModelFolder` overrides it), in Azure from the web's image (`/models`, from its base image `sepiabox-web-models`, S-056). Locally the model loads on the first description search. In Production it is loaded in the background as soon as the web starts (a description search during the load waits for it), and `/health` reports `Degraded` while it is unusable. While the files are missing the box is hidden, and it appears once they arrive, without a restart. A file that is not the pinned one, or that ONNX Runtime cannot use, logs one warning and hides the box until the web restarts with the right file; a file that could not be opened is tried again after 5 minutes. Meanwhile `POST /api/search` answers 503 for `filters.visual`, and every other filter keeps working. A description search with other filters (a year, a city) ranks every candidate exactly; one without filters walks the HNSW index for its top results, which is approximate and needs pgvector 0.8 or later (check in Azure with `SELECT extversion FROM pg_extension WHERE extname = 'vector';`; on an older version it ranks exactly too, which is slower but complete). Descriptions are in English: CLIP reads Portuguese poorly, and the question translator (S-025) turns Portuguese questions into English descriptions (D-070).

## Questions

The question box on the timeline (S-025, D-073; counting questions S-026, D-075, answer with a number or a ranking) sends the question's text, today's date, the time zone and the names of the catalog's sources, cities, countries and named people with at least one counted face (at most 500; S-021; never an e-mail address or who said "This is me", D-080), and the names of the family's saved places and which one is home (S-014; never their coordinates or radius, D-083) to Claude Haiku 5.5 through the Anthropic API, and shows the search it was understood as, with chips to remove each part. It needs `Anthropic:ApiKey` (see the prerequisites); without it the box says questions are not set up, and everything else works. A key added to or removed from Key Vault applies within 5 minutes, without a restart. `Anthropic:Model` changes the model (default `claude-haiku-5-5`). **The first question after a day without questions, or after an update that changes the question format, takes about a minute** (measured on 2026-10-22: 50 to 55 s; the API compiles the output format once and caches it for 24 hours from its last use, with its own compile limit of 180 s; then answers take about a second and a half). The box shows "Thinking about your question…" and, after 8 s, why it takes long; one request is allowed 90 s and a whole question 200 s (D-101). To avoid it, showing the timeline with the question box starts one tiny question in the background when none was translated for 12 hours (about a fraction of a cent, a couple a day at most; `Questions:WarmUp=false` turns it off). Asking one question after a deploy is only a courtesy.

Each person may ask `Questions:DailyLimit` questions per day (200 unless set), counted in the library's time zone; after that the box says so and `POST /api/questions` answers 429. The table `question_usage` keeps, per person and day, the number of questions and the tokens Anthropic billed (input, output, cache reads and writes); a person is pseudonymous, the SHA-256 of their lower-cased e-mail address rather than the address. A question Anthropic never answered (busy, unreachable or refused before any token) does not count. The month's tokens, for comparison with the Anthropic Console: `SELECT sum(input_tokens), sum(output_tokens), sum(cache_read_input_tokens) FROM question_usage WHERE day >= date_trunc('month', now());` in the `catalog` database.

**The live golden run** (required before S-025, S-026 and S-054 are done, D-054): with `SEPIABOX_ANTHROPIC_API_KEY` set (see the prerequisites) and Docker running, `dotnet test tests/Sepiabox.Web.Tests --filter "Category=LiveApi"` asks every question of `tests/Sepiabox.Web.Tests/TestData/questions.golden.json` in English and Portuguese and checks that each means its expected query on the file's fixture catalog; a miss is retried once and reported. It first asks the API for its models: a 401 or 403 fails the test with "missing or wrong", which leaves the story `blocked`. With `SEPIABOX_RECORD_GOLDEN=1` it also rewrites `questions.recorded.json`, the responses CI replays, but only when every question passed (retries allowed): a failing run leaves the file as it was and says so; commit that file with the run's result (pass count, retries, model, date) in the PR.

**The live acceptance run** (S-054) is the same for the MVP's end-to-end test: `dotnet test tests/Sepiabox.Acceptance.Tests --filter "Category=LiveApi" --logger "console;verbosity=detailed"` also needs FFmpeg and ffprobe on the PATH. It builds the fixture library, processes, reports, uploads to Azurite and imports it, asks every question of `tests/Sepiabox.Acceptance.Tests/TestData/acceptance.questions.json` in both languages and compares each answer's numbers with `report` and the generator; with `SEPIABOX_RECORD_GOLDEN=1` it rewrites `acceptance.recorded.json`, again only when every question passed. The steps are in S-054's "Recording run".

## Sign-in configuration

The web reads these keys (D-048). Locally they go into the web's user secrets; in Azure into Key Vault, where `:` becomes `--` in the secret name (`Auth--Google--ClientId`, `Access--Emails`). Never put them in `appsettings*.json`.

| Key | Value |
|---|---|
| `Auth:Google:ClientId`, `Auth:Google:ClientSecret` | The Google OAuth client (web application) |
| `Auth:Microsoft:ClientId`, `Auth:Microsoft:ClientSecret` | The Microsoft app registration, for personal Microsoft accounts only, with a client secret |
| `Access:Emails` | The allowed e-mails, separated by commas; casing does not matter. Empty or missing lets no one in. List the address each provider reports for the account: the primary address shown on the Google account page (myaccount.google.com) or the Microsoft account page (account.microsoft.com), not another alias |

A provider without both of its keys is left out (its button is not shown); one key without the other stops the web from starting. A change to `Access:Emails` takes effect when the configuration reloads: locally when the user secrets file changes, in Azure within 5 minutes, when the web reads Key Vault again (S-058). Someone removed from the list loses access on their next request, and an open page within 5 minutes. Locally:

```bash
dotnet user-secrets set "Access:Emails" "<e-mail>,<e-mail>" --project src/Sepiabox.Web
dotnet user-secrets set "Auth:Google:ClientId" "<client id>" --project src/Sepiabox.Web
dotnet user-secrets set "Auth:Google:ClientSecret" "<client secret>" --project src/Sepiabox.Web
```

Without any OAuth client, in Development, `/sign-in` shows an e-mail field instead (it posts to `/dev-login`): it signs in any e-mail on `Access:Emails` without a password, only from the same computer. `/dev-login` answers 404 in every other environment, and also in Development once a client is configured.

## Connecting Google Drive

**Sources** (S-037, D-097) connects a Google account's Drive, read-only, to count its photos and videos; synchronising comes with S-038. It uses the Google OAuth client of the sign-in (`Auth:Google:ClientId` and `ClientSecret`, in user secrets or Key Vault as in "Sign-in configuration"): no new secret. Without that client, **Sources** says Google Drive cannot be connected.

In the Google Cloud Console, for that OAuth client (once, and again for a new host):

1. Enable the **Google Drive API** for the project (APIs and services → Library).
2. On the OAuth consent screen (Testing mode, the two e-mails as test users), add the scope `https://www.googleapis.com/auth/drive.readonly` (Data access). It is a restricted scope: the app stays in Testing mode and is not verified (D-024), which is why a connection expires after 7 days and is made again with **Reconnect**. Publishing the consent screen **"In production"** while it is unverified (Google shows a warning screen and caps the app at 100 users) normally ends the 7-day expiry; that is the owner's choice under D-024, and the app works the same either way.
3. Add the redirect URIs next to the sign-in's (see "OAuth redirect URLs"): `https://localhost:7180/sources/google-drive/callback` locally, `https://<Container Apps default host>/sources/google-drive/callback` and `https://app.sepiabox.com/sources/google-drive/callback`.

The refresh token is stored protected by ASP.NET Data Protection (the same key ring as the sign-in cookie: in Azure the keys are in Blob Storage and protected by the Key Vault key), never in clear text. **Losing that key ring (replacing the Key Vault key or the `dataprotection` blob) makes every stored token unreadable: Sources then asks to reconnect.** **Disconnect** asks Google to revoke the token and deletes it from the database; the token is sent to Google in the body of the request, never in the address, so telemetry that records URLs never sees it; if Google cannot be reached it is deleted anyway, and the app can be removed by hand at https://myaccount.google.com/permissions.

## Emergency shutdown

See `sepiabox-infra/scripts/emergency-stop.sh` (turns off web traffic, stops PostgreSQL and disables the queue; keeps the data). After `resume.sh`, run `sepiabox-import-all` (see "Automatic import") for the manifests uploaded while the queue was disabled. While PostgreSQL is stopped, the hourly `sepiabox-faces` job fails in a few seconds each hour; that is harmless, and its first run after `resume.sh` does what was missed.
