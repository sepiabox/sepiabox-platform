| D-028 | 2026-10-19 | **(default)** When a photo's thumbnails cannot be made (the image does not decode), its manifest is still written without derivatives, the file is reported as a problem and marked failed, and the next `process` tries the thumbnails again. Manifest `derivatives` entries are typed (`name`, `path`, `width`, `height`, `contentType`) in code and in the schema. | Skip the manifest until thumbnails succeed | The file stays catalogued (date, place, duplicates) even when its pixels are unreadable; a retry costs nothing when the image is still broken. |
| D-029 | 2026-10-19 | **(default)** Video derivatives: `poster` (1280) and `thumb-256` WebP from the frame at 10% of the duration, and `proxy-720p.mp4` fitted inside 1280×720 in either orientation (a portrait phone video becomes 720×1280), sides rounded down to even, metadata removed (`-map_metadata -1`, so no GPS). Manifest width, height and duration come from ffprobe (display size, after rotation). `--hw nvenc` uses `h264_nvenc -rc vbr -cq 28`, since NVENC has no CRF. Without FFmpeg, videos are described and marked `Pending`; while FFmpeg stays missing, unchanged pending videos are not read again. | FFMpegCore; scaling by height only (`scale=-2:720`) | No extra dependency; portrait videos keep a 720-pixel short side; the source drive is spared re-reads of large files. |
| D-030 | 2026-10-19 | **(default)** `upload` reads each original once: the SHA-256 is computed while its 8 MB blocks are staged, and the block list is committed only if the hash still matches the manifest. On a mismatch nothing is committed (Azure discards uncommitted blocks after 7 days) and the file is reported. | Hash the file, then upload it | Re-reading ~1.1 TB from a spinning drive just to check it would double the upload time. |
| D-031 | 2026-10-19 | **(default)** Derivative blobs keep their file name, extension included: `derivatives/<sha256>/thumb-256.webp`, `.../proxy-720p.mp4`. Work-folder files (derivatives, manifests) count as uploaded while their size and last write time are unchanged; a changed manifest is always sent again, even if a blob of the same size exists. | `<sha256>/<name>` without extension; hashing every work file on each run | Self-describing blob names; size and write time avoid re-reading gigabytes of 720p videos, and a manifest can change without changing size. |
| D-032 | 2026-10-19 | **(default)** Importing a manifest adds its sources to the asset and never removes any; derivatives and the asset's own fields are replaced by the latest manifest. | Replace the source list with the manifest's | Each `process` work folder only knows the copies it saw, and a second drive's manifest overwrites the same `<sha256>.json` blob, so replacing would forget the first drive. Removing stale sources is left for a later story. Amended by D-036: the union now happens when `upload` writes the blob; the import still only adds sources, as a second line of defence. |
| D-033 | 2026-10-19 | **(default)** Catalog tables and columns use snake_case through `EFCore.NamingConventions` (MIT). | D-034 | 2026-10-19 | **(default)** `sepiabox-worker import --once` skips and logs invalid manifests without recording them, so they are reported on every run, and exits with code 1 when any was invalid (valid ones are still imported); other exit codes are 2 for usage, 130 when stopped (Ctrl+C or SIGTERM) and 1 for any other failure. In local runs only (`ExecutionContext.IsRunMode`) the AppHost starts two run-once resources: `worker-migrate` (`migrate`), which the web and the import wait to complete, and `worker-import` (`import --once`), which may exit with 1 without blocking the web. They are left out of publishing, where a project would become an always-on Container App; the cloud import is a Container Apps job from S-033, and migrations in the cloud are part of S-032/S-033. | Record invalid manifests as imported; exit 0; one worker running `import --once --migrate` that the web does not wait for | Same exit-code rule as `sepiabox-ingest`; an invalid manifest stays visible until it is fixed or deleted. Splitting migration from import lets the web wait for the schema without waiting on (or failing with) the import. |
| D-035 | 2026-10-19 | **(default)** Catalog integration tests build PostgreSQL from `infra/postgres` (D-012); the `SEPIABOX_TEST_POSTGRES_IMAGE` environment variable lets a developer use an existing image instead. CI never sets it. | Always build | Lets tests run where the PGDG/Debian package servers are unreachable, without weakening what CI tests. |
| D-036 | 2026-10-19 | **(default)** `upload` never overwrites a manifest blob blindly: it reads the stored manifest, merges this work folder's manifest into it and writes it back only if the blob is unchanged (`If-Match` on its ETag, or `If-None-Match: *` when new), retrying the read-merge-write up to 5 times on 409/412. Merge (`ManifestMerge`): union of sources by file identity (type, name, path), the newer `modifiedAt` winning; union of derivatives by name, the incoming one winning on the same name and none dropped; the asset's description (date, place, size, embeddings, faces…) comes from the incoming manifest unless it has no derivatives while the stored one has, which marks an unfinished run (a video waiting for FFmpeg, D-029, or a photo that did not decode, D-028). | Overwrite and rely on the import's add-only sources (D-032) | Two drives uploaded before the next import would otherwise lose the first drive's sources and derivatives for good; ETags make the merge safe with uploads from two computers at once. |
| D-037 | 2026-10-19 | **(default)** Catalog times: `captured_at` is `timestamp without time zone` holding the camera's wall-clock time exactly as `process` writes it; a manifest whose `capturedAt` has an offset or `Z` is rejected by the schema (and reported by the import), never converted. `assets.imported_at` is set once, when the asset first enters the catalog; `assets.updated_at` changes on every import that touches it. Source `modified_at` and import times are UTC `timestamp with time zone`. | Accept offsets and convert to local or UTC; one `imported_at` overwritten on each import | `process` never writes an offset, so one means a foreign writer; converting would silently shift photos across midnight. Keeping the first import time answers "what is new in the library". |
